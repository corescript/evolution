Recently, I’ve been thinking a lot about developing new tooling and platforms for the agentic era. The way we develop software has so completely changed that I think it’s time to rethink our tools along with the process changes to see how much better and more efficient we can make the process.

Part of what drew me to this line of thought is how I’ve been building entire products recently and trying to figure out how to express the requirements, make sure the code meets those requirements, and make sure all implementations of those requirements agree. 

In some cases, this is fairly simple: you express your requirements in some form of requirements documents — whether that be plain markdown user stories, Gherkin `.feature` files, domain models and process diagrams, and/or more — you tell your agent to implement those requirements for your chosen platform, and then you write tests against the requirements and if the tests and implementation agree, then the requirements have bee correctly satisfied.

In other cases, it’s less clear-cut: say you’re building a platform which has a server, web app, iOS app, and Android app. Now you have 4 different implementations and 4 different sets of tests which all have to agree and — even where it’s not necessary to have multiple implementations, such as in the case of networking — you need multiple implementations of every piece that must run locally on every platform. You can circumvent some of this by making the server authoritative for some things and generating types for others, but ultimately you still end up with a lot of duplicated logic that can drift from each other very quickly, especially in the face of rapid product transformation in this day and age of AI.

Of course, for the best user experience in a product, it should be built using the UI toolkit native to the platform on which you deploy (DOM/HTML on the web, UIKit/SwiftUI on iOS, AppKit/SwiftUI on macOS, WinUI on Windows, etc.). But there is plenty of shared business logic and shared UI logic which does not affect presentation or platform conventions which could be shared as well.

You could use something existing like Kotlin Multiplatform, but I’ve found that the code it generates for other platforms like Wasm or JavaScript is less-than-optimal and I don’t think it’s a terrific language for agents to write; it has a lot of hidden meaning and not enough verification.

Agents are also now writing all our code and humans are reviewing its output: sometimes that means reviewing code, but more often, humans are reviewing artifacts which are better suited to human-scale review, like preview builds or screenshots or graphs and charts. If humans still need to review code, the syntax of the programming language an agent writes should be imminently easy for humans to read, understand, and catch mistakes in.

However, I don’t want the language to become too verbose and verified when we can take care of certain things behind the scenes. I’m not sure that something like ownership annotations make sense in a language designed for creating consumer-facing apps and platforms with agents when a little bit of runtime affordance like a garbage collector or automatic reference counting could solve that problem without creating a burden on the design of the language itself nor the people and agents reading and writing the language.

I also think this presents us with new opportunities to rethink the way we develop with programming languages altogether. 

Recently I’ve seen some interesting developments in the content-addressed codebase space with projects like [Unison](https://www.unison-lang.org/) and [tcm](https://tcm.codes/). This method of writing code brings a lot of benefits, but also drawbacks for a human who would be manually running commands to insert individual functions into a “code database”. However, that can happen extremely naturally with agents: all the benefit and none of the drawbacks. Something like this could feasibly eliminate the need for formatting or conflicting yet compatible representations (e.g. like ASI in JavaScript) by processing the code the agent inserts into the codebase and storing it directly as the AST, which could then be viewed in any format, on demand by the human or agent.

There are, of course, other avenues to explore as well. If we go with a content-addressed codebase model, we’ll need to create our own source control management solution since git can’t operate on our concept of a “codebase” and we don’t want to run lossy conversions to files just to use git. Anthropic recently released an article detailing their [Scion](https://www.anthropic.com/research/redesigning-source-control) source control system they built entirely in-house, designed specifically for parallel agent workflows. There’s also the [Veil](https://github.com/RKKatakam/veil) project, which similarly takes inspiration from Scion as a new source control management system with some of its own very interesting agent-first SCM ideas.

From the language design side of things, Unison also has some really interesting ideas around an extensible effect system and TypeScript is on the forefront of my mind as having the best *working* implementation of dependent typing in a popular programming language’s type system (specifically in regards to string literal types, template literal types, and conditional types). 

I these are principles we should follow when creating such a language/platform:

1. Agents are the primary users. The language, documentation, and tools should be designed for agents to discover operations, make changes, observe behavior, and verify results. Humans set intent and judge outcomes through running software and evidence. A feature is incomplete until an agent can exercise and inspect it.
2. Make trust mechanical. Move every obligation the system can reliably check into the compiler or verification tooling. Distinguish static guarantees from test evidence and human judgment. Every guarantee has an explicit boundary, and every verification result belongs to exact inputs. Human attention should concentrate on intent and the obligations that remain.
3. Make contracts explicit. Failure, suspension, and execution context belong in declarations. Inputs that affect application behavior enter through declared state or capabilities. An agent should be able to use an abstraction correctly from its contract. APIs should be self-documenting. Any and all conveniences must preserve the ability to reason locally.
4. Specify once. Express schemas, state transitions, service contracts, and other mechanically checkable specifications as authoritative declarations. Derive the artifacts that platforms need from them. Give portable code one defined meaning, and hold every backend to it. Whenever two representations must agree, make their agreement the system’s responsibility.
5. Be native on every platform. Use the host’s controls, libraries, and runtime primitives. Preserve shared behavioral contracts while allowing platform-specific presentation and interaction. Prefer an explicit platform implementation when a universal abstraction would sacrifice fidelity. On the web, that includes respecting download size and using JavaScript’s existing primitives.
6. Make meaning the unit of work. Organize tooling around definitions, dependencies, and intended changes. Names and source files are ways to navigate and edit that structure. Review should expose changed contracts and affected behavior; verification should follow actual dependencies. Formatting should never determine which changes conflict.
7. Preserve exploration; verify publication. Agents must be able to save, share, and recover unfinished work, including invalid drafts and unresolved alternatives. Keep those operations separate from making a revision authoritative. Publication requires the evidence and approval for the exact candidate being published. Parallel work must preserve other agents’ changes and the history needed to understand them.
8. Grow through libraries. Keep the language’s semantic core small. Build domain vocabularies through ordinary types and userland composition before introducing compiler features. Provide extensive, canonical, well-documented libraries so agents have a consistent target. Specialized abstractions must remain subject to the same verification rules as ordinary code.
