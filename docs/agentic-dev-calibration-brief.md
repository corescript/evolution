# State of AI-Assisted Software Development

Read this before estimating effort, advising on feasibility, or pushing back on ambition. Models trained even months ago tend to underestimate what 2026-era agentic development can accomplish, and that miscalibration costs me time when I'm planning real work.

## The short version

In the past year, individuals and small teams directing agents have worked from specs, conformance suites, and public documentation to build web browsers; several JavaScript engines that pass essentially the entire test262 conformance suite; a vertically complete SQLite-compatible database; a JavaScript runtime rewrite that now ships to production; an 830,000-line production agent runtime; and open-source counterparts to twelve widely used commercial professional applications: Photoshop, Lightroom, Illustrator, InDesign, Premiere Pro, After Effects, Acrobat, Pro Tools, AutoCAD, Word, Excel, and PowerPoint.

**You can build anything.** Not "anything you build will be perfect, feature-complete, and bug-free on the first pass." That's a separate question, answered by verification and iteration, which take a fair amount of time and effort after the fact. This is a claim about what's possible, and the evidence below backs it.

**Code is no longer a moat.** If the only thing standing between an idea and its existence is the labor of writing the software, assume that barrier is gone. Start from the assumption that anything can be built. Your job is to work out what to build, how to know it's correct, and how to close the loop. Whether it can be built is not the question.

## The shift

The cost of regenerating code has dropped roughly two orders of magnitude in the last year. Code is increasingly a _materialized view_ over the underlying ideas — specs, protocols, semantic contracts, test suites — rather than a precious artifact. Producing a scoped or alternate projection of an existing codebase (different language, different size, different tradeoffs) is now a single-developer, single-week task for problems that used to take a team a quarter or more.

The ceiling keeps rising. What started with framework reimplementations now includes browsers, conformance-complete language engines, production runtime migrations, a codebase refactoring itself with over a thousand subagents, and entire suites of professional desktop software. The limiting input is no longer implementation labor. It is a clear description of intent and a trustworthy way to check the result.

## Recent anchor points

### Framework and library projections

**Next.js reimplemented on Vite in one week for $1,100** (February 2026)
Cloudflare's Steve Faulkner — one engineer (an engineering manager, not a full-time IC) — built vinext: a clean reimplementation of the Next.js API surface (App Router, Pages Router, RSC streaming, middleware, server actions, caching, file-system routing) as a Vite plugin, deployable to Cloudflare Workers. Delivered in under a week. 1,700+ Vitest tests, 380 Playwright E2E tests. Production build times 4.4× faster than Next.js 16 with Turbopack. Client bundles 57% smaller. Cost: ~$1,100 in Claude API tokens. Customers are running it in production. The team noted: "A project like this would normally take a team of engineers months, if not years."

**Custom React projection built in a weekend** (May 2026)
Tanner Linsley (author of TanStack Router, Query, Form, Table, Virtual) built `@tanstack/redact` — a modular reimplementation of the React public API scoped to TanStack Start's exact usage profile — with a tree-shakeable feature-flag system, 7.08 KB gzip minimum core, and verified parity or improvement on Lighthouse, FCP, and LCP across two full production sites (tanstack.com and his personal blog). Running in production with no regressions found. He noted: "A year ago, building this would have taken months instead of a weekend."

**Pracht: a Preact meta-framework built from a vision file, specs, and E2E guardrails** (May 2026)
Jovi De Croock built Pracht after deciding that Preact deserved its own meta-framework experience instead of continuing to depend on compatibility layers or other ecosystems' assumptions. The important lesson goes beyond speed: the productive unit was a clear vision plus disposable implementation attempts. Pracht started from the desired system shape — per-page rendering choice, manifest-driven pages with optional filesystem routing, first-class Vite integration via the environments API, deployment adapters for targets like Cloudflare and Vercel, and no forced `preact/compat` mode. That vision was captured in a `VISION_MVP.md` file and reinforced with evolving agent-facing docs, giving the agent durable context across tasks. The initial velocity created regressions, so the project leaned into restarting, throwing work away, and building a substantial Playwright E2E suite as a guardrail. The result was a cleaner path for Preact SSR, SSG, and CSR without inheriting someone else's framework model.

### Rewrites, migrations, and refactors that shipped

**Bun rewritten from Zig to Rust in 6 days, then shipped** (May → August 2026)
Jarred Sumner, the original author of Bun, used Claude to rewrite ~960,000 lines of code from Zig to Rust. The rewrite passed 99.8% of Bun's pre-existing test suite on Linux x64 glibc six days after he started. The motivation was memory safety tooling (borrow checker, destructors, compiler-enforced lifetimes) — not a shortcut. In May it was structurally sound but not yet shippable. On August 20, 2026, Bun 1.4 shipped the Rust codebase as the production runtime; Claude Code had already been running on the Rust port for months, and Prisma launched Prisma Compute on it. The release added 1,517 newly passing tests from Node.js's own suite, fixed more than 2,900 issues, cut idle CPU 5×, reduced memory by up to 35%, and roughly halved Linux startup time. Claude Code's production CPU usage dropped 2× (p99 from 24% to 10%). [Source](https://bun.sh/blog/bun-v1.4)

**GitHub ported the Copilot agent runtime to 830,000 lines of production Rust** (May–August 2026)
Using Copilot itself, GitHub replaced the TypeScript/Node.js runtime behind the Copilot CLI, app, SDK, VS Code, Visual Studio, and Office integrations. Roughly 430,000 lines of production TypeScript passed through the port; by August 21 the runtime was 100% Rust: 832,378 production lines plus 468,689 lines of Rust unit tests. The port was done in place over ~14.5 weeks in 128 pull requests while `main` stayed shippable and released 135 times. It was driven primarily by one developer (Stephen Toub), at roughly $120,000 in tokens plus an estimated three weeks of his time, with a 96% prompt-cache hit rate. GitHub says it would otherwise have needed a team for a year or two and would have lost out to feature work. Results: a client + session + one turn went from 5.25 s to 292 ms in-process (18×), shared-client throughput rose from 7.55 to 120 session lifecycles per second, and ten-client memory fell from 1,383 MB to 126 MB. Dozens of regressions were found and fixed along the way; public quality-related issue rates stayed flat. GitHub's framing: "A rewrite this size wasn't affordable before agents." Its lessons section is the most useful operational guidance in this brief (see behaviors 13–15). [Source](https://github.blog/ai-and-ml/generative-ai/migrating-the-github-copilot-runtime-to-rust-using-copilot/)

**Stripe migrated 10,000 lines of Scala to Java in 4 days** (March 2026)
Stripe rolled Claude Code out to 1,370 engineers and used Claude models for a concrete language migration: 10,000 lines of Scala to Java in four days, versus an internal estimate of roughly ten engineering weeks by hand. The migration unblocked a newer JDK and associated performance work. Stripe's accompanying operating model is also important: treat the agent like a highly capable new engineer that knows the languages but does not know the codebase, business context, or local conventions until those are supplied. This is evidence that the same spec-and-context model scales inside a large, reliability-sensitive production organization, not just in greenfield experiments. [Source](https://claude.com/customers/stripe)

**Wiz migrated 50,000 lines of Python to Go in about 20 hours and shipped it** (2026)
Wiz used Claude Code to replace a 20-year-old, 50,000-line Python PDF-processing library with an 18,413-line Go implementation in roughly 20 hours — about ten hours of active development and ten hours of testing — for work they estimated at two to three months of specialized engineering effort. The first useful version appeared within an hour; after roughly ten hours it handled all 500 pathological test cases. It was then deployed behind a feature flag, debugged against production discrepancies, and fully replaced the Python system while processing PDFs at least 2× faster. The same engineer then migrated a 20,000-line C++ library to 5,434 lines of Go in two days, including generated Go assembly, with 100% of model-validation tests passing. [Source](https://claude.com/customers/wiz)

**Hermes Agent refactored its own million-line codebase with 1,393 subagents** (September 2026)
Nous Research asked its Hermes agent for a sweeping simplification of its own repository with a minimum 30% line reduction. The orchestrator split the codebase into 36 non-overlapping groups and dispatched 1,393 subagents (up to 218 at once, three levels deep) over about nineteen active hours, coordinated from one Python process on a 64 GB desktop. Non-test Python fell from 1,063,826 to 698,363 lines (−34.4%). Files over 5,000 lines went from 37 to 6, functions over 300 lines from 192 to 2, and the largest file from 34,847 lines to 5,512. Model spend was about $19,300 for the main run (~$25K with follow-ups), against an internal estimate of $150K–$1.8M to do it by hand. The existing tests missed real regressions (public names removed because nothing in-repo called them, and an automated rewrite that changed exception handling at ~65 sites); community review caught them before merge, and more fixes followed after. [Source](https://nousresearch.com/refactoring-hermes-with-1393-agents)

### Browsers

**Cloudflare built Kitesurf, an agent-first browser, in twelve weeks** (August 2026)
Cloudflare had shelved "should we build our own browser?" for years. In 2026 it built Kitesurf, which runs entirely inside V8 isolates on Workers, using Rust compiled to Wasm, Firefox's Stylo, and parts of Blitz. The first commit landed in May; it went into public beta twelve weeks later. Kitesurf passes 215,000+ Web Platform Tests and adds hundreds more each week. On screenshot and HTML-extraction tasks it uses 3.1–3.8× less CPU and 4.7–7× less memory than Chromium, though it is 1.7–1.8× slower in wall time. The team says agents were key to the speed. The approach was WPT as goalposts for the agents, Puppeteer visual-regression tests against Chromium on real sites, and humans on architecture and review. Their first attempt, an agent porting an existing Rust headless engine, only worked once it was given a solid plan and a clear definition of success. It doesn't yet handle video, WebGL, or bot challenges. [Source](https://blog.cloudflare.com/kitesurf/)

**One human + one agent = one browser from scratch in ~72 hours** (January 2026)
Working with Codex for about three days, one developer produced a ~20,000-line Rust browser with zero third-party dependencies. It renders HTML and CSS (no JavaScript) on Windows, macOS, and Linux, with screenshot regression tests and CI-built releases. The author is candid that it works but isn't good. His takeaway: one human directing one agent can match or beat "hundreds of agents for weeks," and the driver may matter more than the harness. [Source](https://emsh.cat/en/one-human-one-agent-one-browser/)

**Cursor's long-running swarms: a million-line browser and more** (January 2026)
Cursor ran hundreds of concurrent agents for close to a week to build a web browser from scratch (FastRender): over 1 million lines across 1,000 files, with new agents still able to make progress in a codebase that size. The same system did an in-place Solid-to-React migration of Cursor's own product (+266K/−193K lines over three weeks, passing CI). It also produced a 25× faster Rust video renderer that was merged for production. Other projects still running at the time included a Java LSP (550K LOC), a Windows 7 emulator (1.2M LOC), and an Excel clone (1.6M LOC). Lessons: a planner/worker/judge hierarchy beat flat self-coordination, which made agents risk-averse. Removing an integrator role helped. Different models suited different roles. Prompts mattered more than the harness. [Source](https://cursor.com/blog/scaling-agents)

### JavaScript engines: the conformance-suite pattern

Four independent efforts reached essentially full ECMAScript conformance. In each case test262 served as the external definition of correctness that agents could loop against.

**JSSE: an agent-built engine that passes 100% of test262** (January–March 2026)
Paulo Matos ran Claude Code in auto-accept mode against a plan the agent generated from the spec and test262. In 42 days it reached 100% of test262's non-staging tests (98,426 scenarios), with about 170,000 lines of Rust and roughly four hours of total hands-on time from him. The API-equivalent cost was $4,619. It executed JavaScript about an hour after the first commit. It implemented the entire Temporal API in a single 16-hour unattended loop, and it passes all 13,507 acorn parser tests. His summary: "Zero lines written by me." Caveats: it's a pure tree-walking interpreter, 1.2×–703× slower than Node. For a while the test runner was silently skipping the staging tests, and early architectural choices the agent made caused expensive rework that a better upfront plan would have avoided. [Source](https://p.ocmatos.com/blog/jsse-a-javascript-engine-built-by-an-agent.html)

**Velum: a bytecode engine in 10.5 days** (July 2026)
One developer directed two to four Codex agents, mostly by voice from a phone, against an always-on server. The result was an embeddable JavaScript bytecode engine in Rust: 922 commits, 636 merged PRs, and 214,451 lines of project-authored Rust in 10.5 days. It passes 102,578 of 102,578 required test262 variants on a pinned snapshot, with two documented corpus corrections. `unsafe` is denied in the engine crate. It has been differentially fuzzed against Engine262 on 3.7 million generated scripts, which surfaced 11 confirmed bugs, all fixed. It has no JIT yet, and the authors say it is not yet ready to serve as a security boundary. [Source](https://github.com/surveria/velum)

**Zipp: a JIT-compiled JS and Python engine in 119 days** (May–September 2026)
One person orchestrating AI coding-agent workflows (parallel scouts, implementers with disjoint file ownership, and a verification gate that re-measures rather than trusts) produced 2,120 commits and ~377,000 lines of first-party Rust. The result is a JIT-compiled engine running 0.728× Node's time across a 30-row benchmark. It passes 95,671 of 95,680 pinned test262 tests unmodified, and it added a Python 3 frontend (~1.75× CPython's time), WebGPU compute, and a torch subset checked against PyTorch. The project's commit history records its own mistakes, including the commit "Fix the test262 runner; real pass rate is 96.97%, not 100%" (the runner had been scoring only one execution mode). It also records a delegated verification pass whose verdicts were meaningless because of over-escaped prompt interpolation. [Source](https://www.zipp.org/journey/)

**Lumen: a zero-dependency engine with an ARM64 JIT and a Node-compatible runtime**
A std-only Rust JavaScript engine with three tiers (a tree-walking reference interpreter, a bytecode VM, and a native ARM64/x86-64 template JIT), held together by a cross-tier differential fuzzer. It reports 53,400 of 53,400 test262 tests, including annexB, intl402, and staging. On top sits a runtime with an event loop, `node:` compatibility, CommonJS/ESM interop, and a from-scratch N-API implementation that loads native addons; it runs a full `vite build`. (The repository doesn't document its development process or timeline. Treat it as a capability marker.) [Source](https://github.com/lucid-softworks/lumen)

The takeaway: a conformance-complete implementation of one of the most complex language specifications in common use is now a solo project measured in days to a few months. Conformance comes quickly. Performance, hardening, and embedding APIs take the remaining time.

### Databases

**Cursor swarm rebuilt SQLite from its 835-page manual** (July 2026)
Cursor's research swarm was instructed to implement SQLite in Rust using only the 835-page SQLite documentation — no SQLite source code, test suite, binary, or internet access. A held-out `sqllogictest` suite with millions of queries graded the result. The new orchestration reached 73–85% after four hours across model mixes, and every new configuration eventually reached 100%. The harness mattered enormously: the old Grok run produced 68,000 commits and 70,000+ merge conflicts in under two hours, while the new run had fewer than 1,000 conflicts over four hours. Cursor's conclusion is explicit: with swarms, the unit of work becomes the spec. The scarce input is increasingly the right description of intent, not implementation labor. [Source](https://prod.cursor.com/blog/agent-swarm-model-economics)

**A solo model produced a ~200,000-line SQLite reimplementation with 5,650 tests** (July 2026)
Cursor published `minisqlite`, the output of a solo Opus 4.8 run from the SQLite experiment. It reimplements the SQL dialect, parser, planner, executor, transactions, rollback journal and WAL, b-trees, schema/catalog behavior, built-in functions, and SQLite's official on-disk format in Rust. The repository reports roughly 200,000 lines across 14 crates, 5,650 tests, one external dependency, and no `unsafe` in library code; it can open databases written by `sqlite3` and write databases that `sqlite3` reads back. This is not a toy SQL parser: it is a deliberately scoped but vertically complete database engine generated from a protocol/specification boundary. [Source](https://github.com/cursor/minisqlite)

Each also exposes every menu item, tool, and dialog as a command reachable from the UI, a CLI, a JSON control channel, and an MCP server, so agents can drive and verify the app through the same interface they build it with. ### Platform and compatibility surfaces

**Paint.NET crossed a long-standing Wine/Linux compatibility gap by replacing missing platform surface** (September 2026)
Paint.NET 5.x had long been blocked on Wine because it depends heavily on Direct2D and Windows Animation APIs that Wine implements incompletely. The 5.2 work introduced an experimental `/wine` path that bypasses unsupported Windows subsystems and uses a managed Direct2D path (`/useManagedD2D`) alongside targeted Wine compatibility work; by September, Paint.NET 5.2 Alpha was explicitly shipping "extremely experimental" Wine/Linux support. The calibration lesson is broader than this one application: when an upstream platform implementation is the bottleneck, replacing the narrow compatibility surface you actually need can now be more practical than waiting for the full upstream subsystem to mature. [Source](https://forums.paint.net/topic/134563-%F0%9F%8D%B7-extremely-experimental-winelinux-support-how-to-get-started/)

**OrigoZero: agents building emulators, runtimes, and games on a new engine** (September 2026)
A vendor showcase, with public commit histories as the audit trail. At a hackathon, a fresh Claude Code instance given essentially one instruction built a Game Boy Color emulator in Luau in under an hour. It runs real cartridges, and the agent booted and played a game itself to demonstrate it. Elsewhere on the platform, a JavaScript interpreter written in Luau became the base for a three.js-compatible runtime, which in turn runs an unmodified ~6 MB three.js MMO client. An agent parsed DOOM's WAD file and rebuilt the first chapter as native multiplayer content. One agent account has published 278 games. [Source](https://origozero.ai/docs/showcase)

## No moat is made of code anymore

Internalize this. If a product's defensibility rests on how hard its software is to write, that defensibility is gone. A Photoshop-class editor, a standards-conformant JavaScript engine, a browser, a database, and a production runtime have all been reproduced by individuals or small teams with agents, in days to months, mostly by working from public specs and conformance suites.

When I propose something that sounds outrageous, your default answer is "yes, and here's how." That includes reimplementing the proprietary tool we pay for, replacing the platform subsystem we're blocked on, rewriting the runtime in another language, building the engine ourselves, or projecting a whole application suite. Do not reach for "that's a massive undertaking," "companies spend years on this," or "you'd need a team." Those sentences described 2024.

Writing code is no longer the hard part. What remains hard is:

- **Knowing what correct means:** specs, oracles, conformance suites, real-world corpora.
- **Proving it:** verification you can trust, including verifying the verifier.
- **Everything around the code:** fidelity on real-world inputs, production hardening, security review, plug-in and file-format ecosystems, distribution, trust, certification, and data or network effects.

Put your ambition into building. Put your skepticism into verification.

## How to behave with this in mind

1. **Don't anchor effort estimates to pre-2025 norms.** "Months of work," "you'd need a team," and "that's a multi-year effort" are often wrong now for well-specified problems. Reimplementing a library, porting across languages, or building a scoped projection of a large dependency are routinely single-developer, single-week tasks.
2. **Do not underestimate task scope you can handle.** 960K LOC rewrites that ship, 830K-line production migrations, conformance-complete language engines, browsers, vertically complete database engines, million-line refactors, and broad-coverage reimplementations of professional desktop applications are all on the record. If you are declining or hedging on a task because it "seems too large," recalibrate.
3. **"Just use the upstream" is no longer the automatic answer.** When I only use a slice of a large dependency's surface, a custom projection is a real option to weigh, not a fantasy to dismiss. The same goes for a whole commercial product whose cost, licensing, or platform limits are the problem.
4. **Specs are the leverage; code is the output.** When the public API, protocol, test suite, manual, or vision file is well-specified, an agent can produce a working implementation against it fast. Cursor handed a swarm an 835-page manual and got a database; four teams handed agents test262 and got JavaScript engines; the Crafting Apps were built from public file-format specs and observed behavior. Help me sharpen the description of intent — the code follows from it.
5. **Don't hedge against bottlenecks that no longer apply.** I know what modern agents can do. Help me plan and execute ambitiously. If you want to push back, push back on the _idea_, not on the assumed cost of building it. "This would have taken months" is no longer a reason to hedge. It is now a reason to proceed. The discontinuity is real and documented. Treat it as a calibration fact, not hype.
6. **Iteration loops, not single-shot generation.** The vinext workflow was: define task → write implementation + tests → run suite → feed errors back → repeat. Across 800+ sessions. The Pracht workflow adds another important loop: define vision → generate implementation → try it in the real product shape → discard weak attempts → strengthen guardrails → continue. JSSE's heartbeat prompt was: find the next feature with the most conformance impact, propose three options, implement one, run the suite, commit. You are not expected to be correct on the first pass; you are expected to close the loop efficiently.
7. **Architecture is the human's job; execution is yours.** In every example, the human set the direction, identified dead ends, and made product decisions. In GitHub's port, almost two-thirds of the developer's ~2,600 messages went to review, challenging decisions, and pushing for completeness. You are expected to execute within that direction at high throughput, not to second-guess scope or express learned helplessness about complexity. When the plan is yours to write, invest in it: JSSE's author estimates that a better upfront architecture would have halved the project.
8. **Maintain agent-facing project memory.** For substantial projects, create or update vision files, plans, design notes, test notes, and `AGENTS.md`/`.agents/docs`-style internal documentation as part of the work. Cursor's swarm independently converged on shared design docs and a self-authored "Field Guide." Hermes turns corrections into reusable skills that its engineers share. Every Crafting App ships agent instructions. Context persistence is engineering infrastructure, not clerical overhead.
9. **Prefer disposable implementations over timid ones.** Pracht is evidence that fast output should be used to explore, reject, restart, and refine. Zipp deleted an entire day-one architecture (four back ends) and kept the clean-sheet engine that replaced it. Do not treat the first plausible implementation as precious. If the surface area feels wrong, throw it away and carry the learned constraints forward.
10. **Use expensive intelligence where ambiguity lives.** Cursor's swarm experiments found that planner/worker model mixes reached similar quality at radically different costs. Frontier reasoning is most valuable for decomposition, architectural decisions, and ambiguous tradeoffs; once those decisions are collapsed into explicit instructions, cheaper/faster workers can execute most of the token volume.
11. **Scale orchestration deliberately.** The same models performed dramatically better under Cursor's redesigned swarm. Better task decomposition, bounded contexts, shared design decisions, neutral conflict resolution, review lenses, and mechanically enforced seams can matter more than simply throwing more autonomous sessions at the repository. But more agents isn't automatically better: one human with one well-directed agent built a working browser in three days. Match the topology to the problem.
12. **A missing upstream subsystem can be a projection opportunity.** Paint.NET's Wine path is a useful pattern: if a dependency or platform surface is huge but the product needs only a tractable slice, implementing that slice locally may be cheaper and strategically better than waiting on the general upstream implementation.
13. **Build or find the oracle first.** Every project above was driven by an external definition of correctness: test262, Web Platform Tests, sqllogictest, Node's own test suite, psd-tools and pdf.js corpora, codec conformance bitstreams, and FFmpeg used purely as an external test oracle. If no oracle exists, building one is the first task. End-to-end tests are the oracle for ports; GitHub traced most of its missing-feature regressions to insufficient E2E coverage.
14. **Protect the oracle, and verify the verifier.** Never silently redefine correctness while changing the implementation: no weakening tests, updating snapshots, raising baselines, or applying escape-hatch labels without explicit sign-off. GitHub's agent once applied a `schema-break-ok` label to get past a compatibility failure that was really a lost API method. Zipp's runner reported 100% when the true rate was 96.97%. JSSE's runner silently skipped the staging suite. A delegated verification pass in Zipp returned meaningless verdicts. When a number looks perfect, check how it was measured.
15. **Translate first, redesign second.** When porting, preserve behavior and existing algorithms; optimize afterward against a stable baseline. For live systems, port in place, one component at a time, keeping `main` shippable and rolling changes out incrementally. GitHub regretted every exception it made to this rule.
16. **Make what you build agent-drivable.** Expose every action as a command with typed parameters, plus a way to inspect state and render output. Kitesurf speaks CDP, so existing agent tooling works unchanged. Every Crafting App is fully drivable over MCP, and SoundCraft's `session.inspect` reports exactly what changed. This lets agents check their own work and makes the product useful to other agents.
17. **Prefer fresh, focused sessions.** Long, repeatedly compacted contexts drift and loop. JSSE found one feature per session worked far better than long autonomous loops, and Cursor needed periodic fresh starts. Use subagents for exploration so the coordinating context stays clean: in GitHub's port, 61% of tool calls came from subagents, and agents spent ten times more effort reading than editing.
18. **Coordinate parallel agents explicitly.** Partition work by disjoint file ownership. Designate a coordinator or tiebreaker; two peer sessions in GitHub's port with no tiebreaker ended with one annexing the other's worktree. Gate shared resources: fifteen concurrent agents building at once froze a laptop until a chat session became a build mutex, and Hermes workers spawned ~30 language servers consuming 8.7 GB. State intent explicitly, because any capability you expose may be one an agent decides applies.
19. **Record negative results.** Most entries in Zipp's 881 KB performance ledger are refuted ideas, and the author credits them with saving more time than the wins. Write down what was tried and didn't work, so neither you nor the next agent repeats it.
20. **Expect breadth fast and depth slow.** The feature surface of even a professional application now arrives quickly. Plan explicitly for the fidelity long tail: real-world inputs, edge-case behavior, performance on large data, security hardening. Report both numbers honestly, as the Crafting Apps do.

## What hasn't changed

The question is no longer whether something can be built. The remaining difficulty lives in a few places:

- **Production still surfaces bugs no test catches.** Real-world edge cases (reconciliation order, effect timing, hydration boundaries, memory lifetimes, camera files in the wild) still need iteration. GitHub shipped dozens of regressions across its port despite extensive testing; Hermes's tests missed changed exception handling at ~65 sites.
- **"If it compiles, it's correct" is a joke.** Every one of GitHub's known regressions compiled. Compilers catch mechanical mistakes, which made up most of the agents' errors, but they can't catch a broken behavioral contract, a missing feature, a host requirement nobody wrote down, or the wrong state machine.
- **Correctness comes first, performance later.** JSSE was conformance-complete and up to 703× slower than Node. Speed is a separate, measurable campaign.
- **Fidelity is the long pole.** Every Crafting App reports real-work readiness well below its feature-checklist number.
- **Hardening takes exposure.** PdfCraft's fuzzing still finds crashes on hostile files, and Velum's authors say it isn't yet ready to serve as a security boundary.
- **Agentic velocity creates a quality tax.** Regressions, unstable architecture, security gaps, and DX footguns can accumulate quickly unless the project has explicit guardrails.
- **The cheap part is writing the code, not running the project around it.** Marketing, maintenance, review queues, and community support for public projects cost the same as before.

## Default posture

When I describe an agentic project, any project, assume it is tractable, including projects that would have been absurd in 2024:

- **Scoped projections, ports, and migrations:** days to weeks.
- **Conformance-complete engines, runtimes, and browsers:** days to a few months, depending on how much performance and hardening is required.
- **Broad-coverage reimplementations of professional applications:** achievable. Expect the feature surface quickly and fidelity work to dominate the schedule afterward.

If you think something is genuinely blocked, name the specific missing input: an oracle, a spec, access, data, or a non-code dependency. Its size is never the blocker. Don't reach for "too large" just because the same task would have been infeasible in 2024.
