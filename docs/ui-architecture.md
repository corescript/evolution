# UI Architecture

The one rule behind every entry: **nothing is ambient.** Every input to behavior is either a declared value in the spec or a function of `State`. Anything that can't be declared and mechanically checked across platforms is not architecture.

## Component

- **Initializer**: `(Params) → (initial State, Effect[])`. `Params` are init-time values from the caller — route arguments, a tapped ID, a deep-link payload, a prefetched value. Declared as a table (param condition → initial State + initial Effects), tested like Update rows. For server-driven UI, the server loader _is_ the Initializer, running server-side: it executes the initial Effects and ships the resulting State.
- **State**: stored and derived, **marked in the spec**. Stored fields are facts the machine was told; derived fields are computations over stored fields and **never appear in a transition row's State′ column** — they are recomputed, never assigned. State is an immutable record with fields of data (using a closed union of cases for fields where illegal states unrepresentable), value-comparable (every transition test is an equality assertion), and serializable in principle (a State is a replayable bug report).
- **Action**: the complete vocabulary of things that can happen to a component, each with an optional payload. Three provenances, grouped in the spec because each has a different producer and a different audit trail:
  - **Intents** come from the View — the user did something semantically meaningful (`DeleteConfirmed(id)`, never `SwipeEnded(velocity)`)
  - **Completions** come from `Effect`s — one-shot async work finished (`LoadSucceeded(items)`)
  - **Emissions** come from `Subscription`s — a continuous source produced a value (`ItemsChanged`, `WentOffline`)
  - Every Completion must trace to a declared Effect; every Emission to a declared Subscription; orphan Actions are dead vocabulary and flagged.
- **Update**: pure transition function `(State, Action) → (State′, Effect[])`. No clock, no random, no I/O — time and chance enter as Action payloads or via a Service-backed Effect. Total: every `(state, action)` pair is defined, with the standing invariant that unlisted pairs are _unchanged, no effects_ (enforced by a generated test — stale completions and double-taps are provably inert). One spec row = one clause = one tagged test, in table order.
- **Effects**: descriptions of side-effecting work, returned from `Update` as values (most rows return none; some return several — hence the list). Interpreted by the runtime shim against `Service`s, never executed by the machine. Each Effect declares:
  - **payload** — typed inputs
  - **completions** — which Completion Actions it can resolve to (`FetchItems → LoadSucceeded | LoadFailed`)
  - **key** — identity for cancellable work; transition rows may declare cancellations by key ("entering Loading cancels `search`")
  - **concurrency policy** — what happens when re-requested while in flight: `latest` (cancel the old — search-as-you-type), `drop` (ignore the new — submit buttons), or `queue` (ordered writes); debounce/throttle are parameters of the policy, declared here, not improvised in views
- **Subscriptions**: sources in the form of `Observable<Action>[]`, started on view mount and cancelled on view cleanup; every value emitted is routed into `Update`. Two disciplines keep this portable:
  - each platform defines **what mount/cleanup means there** — server-driven UI never mounts on the server; a covering sheet or backgrounded app is or isn't a cleanup _by declared platform convention_, not by accident of the platform's callback timing
  - a subscription may declare an optional **state predicate** (`while: state.isEnabled`) gating it within the mounted window, so "live-update only once data exists" is spec'd, not improvised
  - Spec-governed continuous sources (live updating queries, sockets, push, timers, connectivity) flow only through Subscriptions — no ad-hoc listeners. Interpretation is per-platform: the same declared subscription may be a Convex live query on web, push-triggered refetch on iOS, a poll elsewhere; if freshness differences matter to the product, the spec says so.
- **View**: renders a view as a function of the current `State` — declaratively, by reconciling mutation — and dispatches **Intent** Actions. One rendering per State value, exhaustive. Below Action granularity (gestures, animation, scroll physics, haptics, focus, how a confirmation is presented), the platform governs the interactions and presentation. Transient view-local state (text composition, cursor, scroll offset, hover) does not round-trip through the machine: _if the spec would ever mention it, it's State; if only the renderer cares, it's view-local_ — promoting one to State is an explicit spec change. Render-only ambient context (theme, locale, size class) is consumed by the View and never seen by the machine.

## System

- **Services**: named capability contracts with per-platform implementations. The contract (something like a Convex schema, an OpenAPI document, or a SQL DDL) enumerates operations with typed inputs, typed outputs, and enumerated failures from the Error catalog. **Effects are requests; Services are fulfillment** — the shim resolves each Effect against a Service, and swapping the interpreter for an in-memory fake is the entire testing story above the unit level. Data services can **two-layered** (remote contract + local-first cache) and the **sync policy between layers should be part of the contract** — read-through, stale-while-revalidate, write-behind, offline queue — not an implementation mood. Ambient nondeterminism (Clock, Random, UUID) is a Service like any other, which is what keeps Update pure and tests synchronous. Services are injected at the composition root; no machine constructs its own.
- **Lenses**: how components compose. A child machine is embedded via a **State Lens** (parent State contains child State) paired with an **Action Prism** (parent Action wraps child Action); the parent's Update delegates wrapped Actions to the child's Update and merges returned Effects. Conventions that ride along:
  - **delegate actions** — children emit facts about themselves (`Delegate.ItemDeleted(id)`); the parent observes during delegation and reacts in its own table; children never reach upward, siblings always coordinate through the common parent
  - **optional-child presentation** — `detail: ItemDetailState?` where non-null _is_ presented and null-ing _is_ dismissal; modality becomes diffable state with show/dismiss rows
  - **keyed collections** — lists of child machines identified by stable IDs
  - Lenses are also the pressure valve for Update: a table past ~a dozen rows is usually multiple machines wearing a trench-coat — decompose, don't get cleverer.
- **Navigation**: which machines are alive and visible is itself State. A **Route Map** is a machine whose State is the route structure (stack / tabs-of-stacks / optional modals), whose cases each carry the `Params` (or embedded State) of their screen, and whose Actions are `Push`, `Pop`, `SwitchTab`, `DeepLink(url)`, etc. — all with transition rows, all tested. Reconciliation per platform: on web the URL is the serialized navigation State (bidirectional mapping; deep linking is free); on native the platform's navigation machinery is _driven from_ State, and user-initiated navigation the platform performs first (back gesture, swipe-to-pop, predictive back) is intercepted and reflected as an Action so state and screen never disagree. A deep link is just `Params` arriving from the OS: parse table → navigation Initializer → per-screen Initializers — covered tables make "does the share link open the right screen?" a unit test.
- **Errors**: an enumerated catalog (`errors/` specs), wired in by three rules:
  - **boundary** — platform exceptions are translated into catalog cases inside Service interpreters and nowhere else; above that line only spec'd errors exist in Actions, State, and tables
  - **classification** — every catalog entry is `recoverable` (retry meaningful: network, timeout), `terminal` (retry pointless: not-found, permission), or `escalate` (routes to another machine: auth expiry → session). Classification mechanically drives Update rows — recoverable Failed states offer retry; terminal ones don't pretend
  - **presentation** — how each classification renders (inline state / toast / blocking dialog) is declared once in the design-system spec; catalog entries carry user-facing copy keys
